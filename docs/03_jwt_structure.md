# 03. JWTの構造

## JWTは暗号化ではない

最初に誤解を解く。JWT (JSON Web Token) は**暗号化されていない**。base64urlで**エンコード**されているだけで、誰でもデコードして中身を読める。JWTが提供するのは機密性(中身を隠すこと)ではなく、**完全性と発行元の証明**(改ざんされていないこと・正しいサーバが発行したこと)。

トークンは3つの部分をピリオドで繋いだ文字列。

```
header.payload.signature
```

- **header**: `{"alg":"HS256","typ":"JWT"}` — 署名アルゴリズム
- **payload**: `{"sub":"alice","role":"user","iat":...,"exp":...}` — クレーム(主張)。ユーザーIDや権限など
- **signature**: `header`と`payload`を繋いだ文字列を、サーバだけが知る秘密鍵で署名したもの

各部分は「JSON文字列をbase64urlエンコードしたもの」であり、パディング(`=`)を省く点が通常のbase64と違う。

## 手でデコードしてみる

`stage2-jwt-alg-none`を起動してログインし、トークンを取り出す。

```
go run ./cmd/stage2-jwt-alg-none
```

```
curl -c /tmp/cookies.txt -X POST localhost:8080/login \
  -d '{"Username":"alice","Password":"password123"}'
grep access_token /tmp/cookies.txt
```

`access_token`の値を`.`で3つに分割し、最初の2つをbase64urlデコードする(3番目のsignatureはバイナリなのでデコードしても読めない)。

```
echo -n '<headerの部分>' | base64 -d
echo -n '<payloadの部分>' | base64 -d
```

`role":"user"`がそのまま読めることを確認する。**JWTのpayloadは平文と思ってよい** — パスワードやクレジットカード番号のような機密情報を入れてはいけない理由がここにある。

## 署名の役割

署名があることで、サーバは「このpayloadは自分が発行したときから1文字も変わっていない」と検証できる。逆に言えば、**検証(Verify)を正しく実装しない限り、署名は何の意味も持たない**。次章以降で攻撃するのは、まさにこの検証ロジックの穴。

## Cookieセッション vs JWT

| | Cookieセッション | JWT |
|---|---|---|
| サーバの状態 | 必要(セッションストア) | 不要(自己完結) |
| スケールアウト | セッション共有の仕組みが要る | 検証鍵さえ配れば水平展開しやすい |
| 即時失効 | 簡単(サーバ側で削除するだけ) | 難しい(トークン自体は期限まで有効であり続ける) |
| トークンの中身 | 意味を持たない参照キー | 署名付きの自己主張データ |
| 盗まれたときの被害 | サーバ側で無効化すれば止まる | 有効期限が切れるまで使われ続ける |

この表の「即時失効が難しい」という弱点を、stage5でどう補うかが8章のテーマになる。
