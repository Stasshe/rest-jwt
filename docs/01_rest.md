# 01. RESTの仕組みとフロー

JWTはRESTの上に乗る一部品でしかない。土台であるREST自体の仕組みとリクエスト/レスポンスの流れを、先に体に入れる。

## RESTとは何か

REST (Representational State Transfer) は「こう実装しろ」という規格ではなく、Web APIをこう設計すると良いという**アーキテクチャスタイル**。中心にある制約は次の3つ。

- **クライアント/サーバ分離**: UIとデータ保持を分離する。クライアントが変わってもサーバは変わらない
- **ステートレス**: サーバはリクエスト間でクライアントの状態を保持しない。**1つのリクエストだけを見て、そのリクエストを処理するのに必要な情報が全部揃っている**のが原則(認証情報も毎回そのリクエストに乗っている必要がある — これは2章以降、何を「毎回乗せる」かという話に直結する)
- **統一インターフェース**: 全リソースを同じ流儀(URI + 少数の標準メソッド + 標準的な表現形式)で操作する。エンドポイントごとに独自のやり取りを発明しない

「ステートレス」は次章で見るCookieセッションと真っ向から矛盾する制約であることに注意する。実務ではこの制約を意図的に緩め、その代償(スケールしにくさ、失効の複雑さ)を引き受けている。

## リソースとURI

RESTはURIを「操作」ではなく「モノ(リソース)」として設計する。

- 良い例: `GET /items/42` (リソース`42`を取得)
- 悪い例: `GET /getItem?id=42` (動詞がURIに入っている — RPC的発想)

コレクションとメンバーの2階層が基本形。

```
GET    /items       一覧取得
POST   /items       新規作成(コレクションに対して)
GET    /items/{id}  1件取得
PUT    /items/{id}  置き換え(メンバーに対して)
DELETE /items/{id}  削除(メンバーに対して)
```

## 1往復の中身を分解する

`curl -v`で1往復の生のやり取りを見る。まず`stage1-session`を起動する。

```
go run ./cmd/stage1-session
```

```
curl -v localhost:8080/items
```

出力には`>`(送信)と`<`(受信)でリクエストとレスポンスが両方出る。

```
> GET /items HTTP/1.1
> Host: localhost:8080
> Accept: */*
>
< HTTP/1.1 200 OK
< Content-Type: text/plain; charset=utf-8
<
[{"id":"1","name":"first item"}]
```

リクエストは**リクエストライン**(メソッド + パス + HTTPバージョン)、**ヘッダ**(`Host`, `Accept`など)、空行、**ボディ**(ここではGETなので無し)。レスポンスは**ステータスライン**(バージョン + ステータスコード + 理由句)、ヘッダ、空行、ボディ、という同じ構造を持つ。JWTもCookieも、この「ヘッダに何を乗せるか」という一点に載る話でしかない。

## メソッドの意味論

RESTでは各メソッドに「安全性(safe)」と「べき等性(idempotent)」という2つの性質が仕様上定義されている。これを無視した実装は、ブラウザのキャッシュ・自動リトライ・CSRF対策すべてと噛み合わなくなる。

| メソッド | 安全(副作用なし) | べき等(同じ結果を何度でも) | 典型用途 |
|---|---|---|---|
| GET | ○ | ○ | 取得 |
| HEAD | ○ | ○ | ヘッダのみ取得 |
| PUT | × | ○ | 置き換え |
| DELETE | × | ○ | 削除 |
| POST | × | × | 作成・非べき等な処理 |
| PATCH | × | × | 部分更新 |

「安全」はリソースの状態を変えないこと。「べき等」は1回叩いても100回叩いても、サーバの最終状態が変わらないこと(レスポンス自体は変わってもよい)。GETに副作用を持たせたり、PUTを非べき等に実装したりすると、この表を信じて作られたブラウザやキャッシュ、リトライ機構の前提が崩れる。

## ステータスコードは分類で覚える

| 範囲 | 意味 |
|---|---|
| 2xx | 成功。`200 OK`, `201 Created`, `204 No Content` |
| 3xx | リダイレクト。`301`, `304 Not Modified` |
| 4xx | クライアント側のエラー。`400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found` |
| 5xx | サーバ側のエラー。`500 Internal Server Error` |

401と403は特に区別が必要。401は「あなたが誰か証明できていない」、403は「誰かは分かったが権限がない」。この区別自体が、機密度の高いリソースでは「存在するかどうかを隠すために403の代わりに404を返す」という設計判断につながる(正解が一つに決まる話ではない)。

## ハンズオン: メソッドとステータスコードを動かして確認する

```
# 一覧(安全・べき等) — 何度叩いても状態は変わらない
curl -i localhost:8080/items

# 未認証でPOST(非べき等な操作は保護されているべき) → 401
curl -i -X POST localhost:8080/items -d '{"Name":"x"}'

# ログインしてから作成 → 201 Created、Locationヘッダに新しいリソースのURI
curl -c /tmp/cookies.txt -X POST localhost:8080/login \
  -d '{"Username":"alice","Password":"password123"}'
curl -i -b /tmp/cookies.txt -X POST localhost:8080/items -d '{"Name":"widget"}'

# 同じPUTを2回叩く → べき等なので結果は変わらないことを確認
curl -i -b /tmp/cookies.txt -X PUT localhost:8080/items/1 -d '{"Name":"renamed"}'
curl -i -b /tmp/cookies.txt -X PUT localhost:8080/items/1 -d '{"Name":"renamed"}'
curl localhost:8080/items
```

`201`のレスポンスヘッダに`Location: /items/2`のようなURIが乗っていることを確認する。「作成した場所を教える」のもRESTの流儀の一つ。

## ステートレス性とセキュリティ

RESTは「サーバは状態を持たない」ことを理想とするが、認証は「このリクエストは誰のものか」という状態そのものを要求する。ここに矛盾があり、次章のCookieセッションは「サーバ側に状態を持つ」ことでこれを解決し、3章以降のJWTは「リクエスト自体に署名付きで状態を埋め込む」ことでこれを解決する。どちらもトレードオフであり、この対立を意識しながら読み進める。

また、べき等性の話は攻撃面にも直結する。ブラウザは`<form>`や`<img>`タグから単純な`GET`/`POST`をクロスサイトに送れてしまう(CSRFの土台)。副作用のある操作を安全であるべきGETに実装する、認証なしでPOSTを通す、といった設計ミスは、この意味論を破っているという意味でも即座に危険と分かる。
