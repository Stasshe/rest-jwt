# 01. RESTとセキュリティ

JWTを理解する前に、JWTが乗る土台であるRESTの性質を、セキュリティ視点で押さえる。

## リソースとメソッド

RESTはURIを「リソース」として扱い、HTTPメソッドで操作の種類を表す。

- `GET /items` — 一覧取得(副作用なし)
- `POST /items` — 新規作成(非べき等。2回叩くと2件増える)
- `PUT /items/{id}` — 置き換え(べき等。同じボディを何回送っても結果は同じ)
- `DELETE /items/{id}` — 削除(べき等。2回目は「既に無い」だけ)

このべき等性の区別は攻撃面に直結する。ブラウザは`<form>`や`<img>`タグから単純な`GET`/`POST`をクロスサイトで送れてしまう(CSRFの土台)。だから「副作用のある操作をGETに実装する」「認証なしでPOSTが通る」は設計ミスとして即座に危険と分かる必要がある。

## ステータスコードは情報

- `401 Unauthorized` — 誰であるか証明できていない(未ログイン)
- `403 Forbidden` — 誰であるかは分かったが権限がない
- `404 Not Found` — リソースが存在しない

401と403を意図的に混同し、権限がない場合も404を返す設計がある(「存在するかどうか」自体を隠す)。どちらを選ぶかはリソースの機密度次第の設計判断であり、雑にどちらかへ倒すものではない。

## ステートレス性

RESTの原則の一つは、サーバがクライアントの状態(セッション)を保持しないこと。しかし「認証」は本質的に状態(このリクエストは誰のものか)を必要とする。この矛盾をどう解決するかが、これから見るCookieセッションとJWTそれぞれのアプローチの違いになる。

- Cookieセッション: サーバがセッションIDと紐づく状態を保持する → 原則から外れるが失効が簡単
- JWT: 状態を持たず、リクエスト自体に署名付きで「誰であるか」を埋め込む → 原則には忠実だが失効が難しい

この対立を意識しながら次章に進む。

## ハンズオン

`stage1-session`を起動する。

```
go run ./cmd/stage1-session
```

別ターミナルで:

```
# 未認証でGET(公開リソースなので通る)
curl -i localhost:8080/items

# 未認証でPOST(401になるはず)
curl -i -X POST localhost:8080/items -d '{"Name":"x"}'
```

401が返ることを確認する。ステータスコードだけでなく、ボディの`{"error":"login required"}`も見て、「なぜ401なのか」をレスポンスから読み取れることを確認する。
