# 09. まとめ

## 4つの攻撃の根本原因

| 攻撃 | 壊れていた確認 |
|---|---|
| BOLA (00章) | 認証はあるが、対象オブジェクトの所有者チェックが無い |
| IDOR (01章) | 認証はあるが、認可の根拠にセッションではなくクライアント入力を使っている |
| セッション固定 (02章) | セッションIDの強さは十分だが、ログイン時に再発行(ローテーション)していない |
| JWT (04〜06章) | 署名検証はあるが、検証方法自体をトークン(攻撃者が作れる部分)に決めさせている |

4つとも表面上のバグは別物だが、突き詰めると同じ形をしている — **「確認している」つもりの箇所が、実は確認すべき相手(本人か・所有者か・鍵は誰のものか)を取り違えている**。認証・認可の実装は、チェックの有無だけでなく「何を根拠にそのチェックをしているか」まで見る必要がある。

## 設計判断の比較表: Cookieセッション vs JWT

| 観点 | Cookieセッション | 素朴なJWT(03〜06章) | JWT+リフレッシュ(08章) |
|---|---|---|---|
| サーバの状態 | 必要 | 不要 | アクセストークンは不要、リフレッシュのみ必要 |
| 即時失効 | 簡単 | 不可能 | リフレッシュを消せば実質可能(アクセスは期限まで有効) |
| 検証コスト | ストア参照 | 署名検証のみ(高速) | 同左 |
| 最大のリスク | セッション固定、CSRF | 検証ロジックの実装ミス(04〜06章) | 検証ロジック + 鍵管理の運用 |

「JWTだからセキュア」でも「セッションだからレガシー」でもない。**何を状態としてサーバに残し、何をトークンに埋め込むか**というトレードオフの選択であり、08章のサーバは実質「短命JWT + サーバ側リフレッシュセッション」というハイブリッドに落ち着いている。

## 本番投入前のチェックリスト

- ログイン成功時に毎回セッションIDを再発行しているか(クライアントが送ってきたIDを使い回していないか)
- 権限判定は「本人か」だけでなく「その対象への権限があるか」まで毎回確認しているか
- 認可の根拠にしているのはセッション/トークン由来の値だけか(クエリパラメータやリクエストボディの識別子を信用していないか)
- 署名アルゴリズムはサーバ側で固定しているか(`alg`ヘッダを信用していないか)
- 鍵は十分な長さの乱数か、辞書に載っていないか
- 公開鍵(RS256等)を別の用途の鍵として使い回していないか
- アクセストークンの有効期限は短いか、失効の手段があるか
- トークンに機密情報(パスワード、カード番号等)を入れていないか(payloadは平文)
- CookieはHttpOnly / SameSite / Secure(本番はHTTPS前提)が付いているか
- 権限判定(RBAC)は、検証済みのクレームだけを根拠にしているか
